# Alert Runbook

This document provides runbooks for common alerts generated by the Goose alerting system.

## Alert Types

### 1. Script Failure (script_failure)

**Severity**: CRITICAL or HIGH  
**Trigger**: Script exits with non-zero exit code

**Symptoms**:
- Script execution fails
- Exit code is non-zero
- Error messages in logs

**Investigation Steps**:
1. Check the script's log file for error messages:
   ```bash
   tail -n 100 /tmp/goose-logs/<script-name>-*.jsonl | jq 'select(.level == "ERROR" or .level == "FATAL")'
   ```
2. Review the metrics file for context:
   ```bash
   cat /tmp/goose-logs/<script-name>-metrics-*.json | jq '.'
   ```
3. Check the trace ID to correlate related logs:
   ```bash
   grep "<trace-id>" /tmp/goose-logs/*.jsonl | jq '.'
   ```
4. Review script exit code and any error messages

**Common Causes**:
- Missing dependencies or tools
- Configuration errors
- Network connectivity issues
- Permission problems
- Resource exhaustion (disk space, memory)

**Resolution**:
1. Fix the underlying issue (missing dependency, config error, etc.)
2. Re-run the script
3. If issue persists, check system resources and permissions
4. Review recent changes that might have caused the failure

**Prevention**:
- Ensure all dependencies are installed
- Validate configuration before running
- Monitor system resources
- Test scripts in isolated environments first

---

### 2. High Error Count (high_error_count)

**Severity**: HIGH or CRITICAL  
**Trigger**: Error count exceeds threshold (default: 1)

**Symptoms**:
- Multiple ERROR or FATAL log entries
- Error count metric exceeds threshold

**Investigation Steps**:
1. Count errors in the log file:
   ```bash
   cat /tmp/goose-logs/<script-name>-*.jsonl | jq 'select(.level == "ERROR" or .level == "FATAL")' | jq -s 'length'
   ```
2. Group errors by type:
   ```bash
   cat /tmp/goose-logs/<script-name>-*.jsonl | jq 'select(.level == "ERROR")' | jq -s 'group_by(.message) | map({message: .[0].message, count: length})'
   ```
3. Check for patterns in error messages
4. Review script execution context

**Common Causes**:
- Systematic failures (all operations failing)
- Configuration issues affecting multiple operations
- Resource constraints
- External service outages
- Data corruption

**Resolution**:
1. Identify the root cause of errors
2. Fix systematic issues first
3. Address configuration or resource problems
4. If external service issue, wait for service recovery
5. Re-run script after fixes

**Prevention**:
- Implement proper error handling in scripts
- Validate inputs and configurations
- Monitor external dependencies
- Set up health checks

---

### 3. Performance Degradation (performance_degradation)

**Severity**: MEDIUM  
**Trigger**: Script execution time exceeds threshold (default: 3600 seconds / 1 hour)

**Symptoms**:
- Script takes longer than expected to complete
- Duration metric exceeds threshold

**Investigation Steps**:
1. Check script duration:
   ```bash
   cat /tmp/goose-logs/<script-name>-metrics-*.json | jq '.duration'
   ```
2. Review span durations to identify slow operations:
   ```bash
   cat /tmp/goose-logs/<script-name>-*.jsonl | jq 'select(.span_id != null) | {span: .span_id, message: .message}' | jq -s 'group_by(.span)'
   ```
3. Check system resources during execution:
   - CPU usage
   - Memory usage
   - Disk I/O
   - Network latency
4. Review recent changes that might affect performance

**Common Causes**:
- Increased data volume
- System resource constraints
- Network latency
- Inefficient algorithms or operations
- External service slowdowns
- Resource contention

**Resolution**:
1. Identify the slow operation(s)
2. Optimize or parallelize operations
3. Increase system resources if needed
4. Cache results where possible
5. Review and optimize algorithms

**Prevention**:
- Set performance budgets
- Monitor resource usage
- Optimize slow operations
- Use caching where appropriate
- Profile scripts regularly

---

### 4. Repeated Failures (repeated_failures)

**Severity**: CRITICAL  
**Trigger**: Same script fails multiple times (default: 3 failures)

**Symptoms**:
- Same script failing repeatedly
- Failure count metric exceeds threshold

**Investigation Steps**:
1. List all failures for the script:
   ```bash
   find /tmp/goose-logs -name "<script-name>-metrics-*.json" -exec jq 'select(.exit_code != 0)' {} \;
   ```
2. Check failure patterns:
   ```bash
   find /tmp/goose-logs -name "<script-name>-metrics-*.json" -exec jq '{exit_code, duration, timestamp: .end_time}' {} \; | jq -s 'sort_by(.timestamp)'
   ```
3. Review error messages across failures
4. Check for environmental changes
5. Review recent code or configuration changes

**Common Causes**:
- Persistent configuration issue
- Environmental problem (missing service, resource)
- Bug in script logic
- Data corruption
- Dependency version mismatch

**Resolution**:
1. Stop automated retries if script is in a loop
2. Investigate root cause thoroughly
3. Fix underlying issue
4. Test fix in isolation
5. Re-enable script after verification

**Prevention**:
- Implement proper error handling
- Add retry logic with exponential backoff
- Validate environment before execution
- Monitor for persistent issues
- Set up circuit breakers for repeated failures

## Alert Configuration

### Adjusting Thresholds

Edit `alert-config.json` to adjust alert thresholds:

```json
{
  "thresholds": {
    "error_count": 5,        // Alert after 5 errors
    "failure": 1,            // Alert on any failure
    "duration_seconds": 1800, // Alert if script takes > 30 minutes
    "repeated_failures": 3,   // Alert after 3 repeated failures
    "error_rate": 0.1         // Alert if error rate > 10%
  }
}
```

### Enabling Alert Channels

#### Email
```json
{
  "channels": {
    "email": {
      "enabled": true,
      "to": "team@example.com"
    }
  }
}
```

**Requirements**: `mail` or `sendmail` command must be available

#### Slack
```json
{
  "channels": {
    "slack": {
      "enabled": true,
      "webhook_url": "https://hooks.slack.com/services/YOUR/WEBHOOK/URL"
    }
  }
}
```

**Setup**: Create a Slack webhook at https://api.slack.com/messaging/webhooks

#### Generic Webhook
```json
{
  "channels": {
    "webhook": {
      "enabled": true,
      "url": "https://your-webhook-endpoint.com/alerts"
    }
  }
}
```

#### PagerDuty
```json
{
  "channels": {
    "pagerduty": {
      "enabled": true,
      "integration_key": "your-pagerduty-integration-key"
    }
  }
}
```

**Setup**: Create a PagerDuty integration and get the integration key

## Alert Deduplication

Alerts are automatically deduplicated to prevent alert fatigue. By default, the same alert won't be sent again within 5 minutes (300 seconds).

To adjust the deduplication window, set the `ALERT_DEDUP_WINDOW` environment variable or modify the deduplication logic in `alerting-utils.sh`.

## Monitoring Scripts

### Running the Monitor

Run the monitor script to watch for alerts:

```bash
# Run once
RUN_ONCE=true ./scripts/monitor-alerts.sh

# Run continuously (daemon mode)
./scripts/monitor-alerts.sh

# Run in background
nohup ./scripts/monitor-alerts.sh > /tmp/monitor.log 2>&1 &
```

### Cron Job Setup

Add to crontab to run monitoring periodically:

```bash
# Check for alerts every 5 minutes
*/5 * * * * /path/to/goose/scripts/monitor-alerts.sh RUN_ONCE=true
```

## Troubleshooting

### Alerts Not Being Sent

1. **Check alert configuration**:
   ```bash
   cat scripts/alert-config.json | jq '.channels'
   ```
   Ensure at least one channel is enabled.

2. **Check alert log**:
   ```bash
   tail -f /tmp/goose-alerts/alert-log.jsonl | jq '.'
   ```

3. **Verify alerting utilities are loaded**:
   Scripts using `logging-utils.sh` automatically load `alerting-utils.sh` if available.

4. **Check network connectivity** (for webhook/Slack/PagerDuty):
   ```bash
   curl -X POST <webhook-url> -d '{"test": true}'
   ```

### Too Many Alerts

1. **Increase thresholds** in `alert-config.json`
2. **Adjust deduplication window** to reduce duplicate alerts
3. **Review alert conditions** - may need to be more specific
4. **Fix underlying issues** causing repeated alerts

### Missing Alerts

1. **Check alert thresholds** - may be too high
2. **Verify alert channels are enabled** and configured correctly
3. **Check alert log** for any errors
4. **Review script exit codes** - ensure failures are being detected

## Best Practices

1. **Start with conservative thresholds** and adjust based on actual usage
2. **Enable multiple alert channels** for redundancy
3. **Review alerts regularly** to tune thresholds and conditions
4. **Document alert responses** in this runbook
5. **Set up alert escalation** for critical alerts
6. **Monitor alert system itself** to ensure it's working
7. **Regularly review and update** alert conditions as system evolves
